# 태그 기능 PRD

## 개요

노트에 태그를 추가/삭제하여 노트를 분류할 수 있는 기능을 제공한다. 태그는 노트 내부에 `string[]`로 저장되며, 노트 편집 화면에서 Chip Input UI를 통해 관리한다. 본 PRD는 `docs/features/tag/spec-fixed.md`(확정본)를 기반으로 한다.

**목표**

- 사용자가 노트에 의미 있는 분류 메타정보를 부여할 수 있게 한다.
- 기존 `Note` 데이터 구조와 `updateNote` API 흐름을 최소 변경으로 확장한다.
- 이후 검색/필터/자동완성 기능의 기반을 마련한다.

**비목표(간단)**

- 태그 기반 검색/필터링, 전역 태그 관리, 자동완성은 포함하지 않는다(상세는 Out of Scope 참고).

---

## 사용자 스토리

### US-1. 태그 추가

> 노트를 작성하는 사용자로서, 제목 아래 입력란에 태그를 입력하고 Enter 또는 `,`를 눌러 칩으로 확정할 수 있다. 그래야 노트를 주제별로 분류할 수 있다.

**수용 기준**

- `NoteEditor`의 제목 바로 아래 Chip Input이 노출된다.
- `Enter` 또는 `,` 키로 입력값이 칩으로 확정된다.
- 입력값은 `trim()` 후 저장되며, 빈 문자열은 추가되지 않는다.
- 대소문자 무시 비교로 중복이면 무시하고 input만 비운다(에러 미표시).
- 1개당 최대 15자, 노트당 최대 10개까지만 추가 가능하며, 초과분은 차단된다.

### US-2. 태그 삭제

> 노트를 작성하는 사용자로서, 칩 위에 마우스를 올리면 나타나는 × 버튼으로 태그를 삭제할 수 있다. 그래야 잘못 추가한 태그를 빠르게 제거할 수 있다.

**수용 기준**

- 칩은 기본 상태에서 × 버튼이 숨겨져 있고, hover 시에만 노출된다.
- × 클릭 시 해당 태그가 즉시 제거된다.
- input이 비어 있는 상태에서 `Backspace`를 누르면 마지막 칩이 삭제된다.

### US-3. 태그 확인

> 노트를 열람하는 사용자로서, 편집 화면에서 해당 노트에 달린 태그 목록을 바로 확인할 수 있다.

**수용 기준**

- `NoteEditor` 내 제목과 본문 사이에 태그 칩 목록이 표시된다.
- 태그가 0개인 경우 placeholder(`태그 입력 후 Enter`)만 표시된다.
- 노트 목록(`NoteItem`)에는 태그를 표시하지 않는다(이번 스코프 제외).

### US-4. 태그 저장

> 노트를 저장하는 사용자로서, 본문을 저장할 때 태그 변경사항도 함께 저장된다. 그래야 별도의 저장 조작 없이 자연스럽게 동기화된다.

**수용 기준**

- 기존 `updateNote` 호출 시 `tags` 필드가 함께 전송된다.
- `updatedAt`은 기존 규칙대로 `src/api/notes.ts`에서 세팅된다.
- 태그 전용 저장 API는 추가하지 않는다.

## 기술 결정 (ADR)

태그 기능의 전체 아키텍처는 **"C안 — 커스텀 훅 기반 합성"**을 채택한다. 선정 이유: 리액트의 순수 API(useState/useEffect/커스텀 훅)를 최대한 활용하고, 로직을 훅으로 분리해 합성 가능한 얇은 컴포넌트를 유지하며, 훅 단위 테스트로 검증 규칙을 격리해 커버할 수 있기 때문이다. 이 방향은 본 기능 이후에도 프로젝트 전반에서 동일하게 이어간다.

### ADR-1. 태그 데이터 저장 구조 — 노트 내부 임베드(`tags: string[]`)

- **Context**: 태그는 노트의 분류/검색 메타정보이며, 이번 스코프는 검색·전역 태그 관리·자동완성을 포함하지 않는다. 저장소는 `json-server` + `db.json`으로 단일 엔티티에 자연스럽게 필드를 추가할 수 있다.
- **Decision**: `Note` 타입에 `tags: string[]` 필드를 직접 추가한다. 기본값은 `[]`. 별도 `tags` 컬렉션/ID 참조 구조를 두지 않는다.
- **Alternatives**:
  - (a) 별도 `tags` 컬렉션 + `note.tagIds[]` 정규화 — 전역 태그 관리/rename에 유리.
  - (b) 태그 문자열을 본문(`content`)에 해시태그로 인라인 저장 — 파싱 기반.
- **Consequences**:
  - 👍 구현이 단순하고 기존 `updateNote` 한 번의 PATCH로 저장이 끝난다. UI/훅/API 변경 지점이 최소화된다.
  - 👎 전역 태그 rename/merge가 필요해지면 전 노트를 순회해야 한다 — 필요 시 마이그레이션으로 정규화 구조로 전환(Out of Scope 참고).

### ADR-2. 태그 상태 관리 위치 — 폼 로컬 상태(커스텀 훅)에 둔다

- **Context**: 프로젝트는 "서버 상태는 `NotesContext`, UI 상태는 `App`, 폼 로컬 상태는 `NoteEditor`"의 3계층 분리를 따른다. 태그는 저장 전까지 편집 중인 폼의 일부이며, 서버 상태로 승격할 필요가 없다.
- **Decision**: 태그 편집 상태는 `NoteEditor` 내부의 커스텀 훅 `useTagInput`에 보관한다. `NotesContext`에는 `addTag`/`removeTag` 같은 도메인 액션을 추가하지 않고 기존 `updateNote(id, updates)` 시그니처를 그대로 사용한다.
- **Alternatives**:
  - (a) `NotesContext`에 `addTag`/`removeTag` 액션 추가(안 B) — 검증을 Context에 집중.
  - (b) 전역 상태 라이브러리(Zustand 등) 도입 — 과한 복잡도.
- **Consequences**:
  - 👍 기존 3계층 규칙·API 동사 네이밍 규칙과 일관. Context는 순수하게 서버 상태만 담당. 훅을 `renderHook`으로 격리 테스트 가능.
  - 👎 여러 화면에서 같은 태그 편집 로직을 공유해야 한다면 훅을 재사용하거나 승격하는 리팩터가 필요.

### ADR-3. Chip Input 컴포넌트 설계 — `useTagInput` 훅 + presentational `TagChipInput`

- **Context**: Chip Input은 "확정된 칩 목록 + 편집 중 input + 키보드 핸들링(Enter/`,`/Backspace) + 검증(trim/중복/길이/개수)"이 얽힌 컴포넌트다. 로직과 뷰가 한 덩어리가 되면 테스트가 어려워진다. 사용자는 훅 기반 합성 방식을 선호한다.
- **Decision**: 로직은 `useTagInput(initialTags, { maxTags: 10, maxLen: 15 })` 훅으로 분리한다. 훅은 다음을 반환한다.
  - 상태: `tags`, `input`, `isFull`
  - 핸들러: `setInput`, `commit`, `removeTag`, `handleKeyDown`
  - 외부 동기화: `reset(nextTags)` (선택 노트 전환 시 사용)

  뷰는 `TagChipInput`이라는 얇은 presentational 컴포넌트로, 훅의 반환값을 props로 받아 JSX에 바인딩만 한다. `NoteEditor`는 훅을 호출하고 `tags` 값을 `handleSave`에서 `updateNote` payload에 포함시킨다.

- **Alternatives**:
  - (a) 단일 `TagChipInput` 컴포넌트 내부에 로직까지 포함(제어형 props만 노출) — 안 A. 파일 수는 적지만 로직/뷰 결합이 강하고 훅 단위 테스트 불가.
  - (b) `react-hook-form` 같은 라이브러리의 field array 사용 — 의존성 추가 부담.
- **Consequences**:
  - 👍 로직은 `renderHook`으로, 뷰는 RTL로 독립적으로 테스트할 수 있다. 향후 다른 화면(예: 필터 입력)에서도 `useTagInput`을 재사용할 수 있다. 프로젝트에 "훅 분리"라는 선례를 남긴다.
  - 👎 파일이 2~3개로 늘어 소규모 기능 치고는 구조가 과할 수 있다. 팀 내에 훅 분리 관례가 아직 없으므로 명명/배치 컨벤션을 함께 정해야 한다(`src/hooks/useTagInput.ts` 위치 제안).

### ADR-4. 검증 규칙 적용 시점 — 입력 시점 차단(훅 내부에서)

- **Context**: spec-fixed의 검증 규칙은 4종류다 — trim 후 빈 값 무시, 대소문자 무시 중복 제거, 태그당 15자, 노트당 10개. 규칙을 입력 시점에 막을지, 저장 시점에 검증할지 결정이 필요하다.
- **Decision**: **모든 규칙을 입력 시점에 `useTagInput` 훅 내부에서 차단**한다.
  - `maxLen(15)`: input의 `onChange`에서 `value.length > 15`면 반영하지 않음(하드 차단).
  - `maxTags(10)`: `isFull`일 때 `commit()`은 no-op. input 자체는 비활성화 또는 포커스 유지.
  - `trim + empty`: `commit()` 내부에서 `trim()` 후 빈 문자열이면 무시.
  - `중복(대소문자 무시)`: `commit()` 내부에서 `tags.some(t => t.toLowerCase() === next.toLowerCase())`이면 input만 비우고 반환(에러 미표시).

  저장 시점(`handleSave`)에서는 별도 재검증을 하지 않는다. 훅이 규칙을 단일 진입점으로 강제하므로 상태에는 항상 유효한 태그 목록만 존재한다.

- **Alternatives**:
  - (a) 입력은 자유롭게 받고 저장 시점에 일괄 검증 + 에러 메시지 — spec의 "에러 메시지 없이 무시" 정책과 어긋남.
  - (b) 저장과 입력 양쪽에서 이중 검증 — 중복 로직.
- **Consequences**:
  - 👍 상태 불변식(invariant)이 단순하다: "`tags`는 항상 유효하다." 훅 단위 테스트로 규칙 4종을 전부 커버하기 쉽다.
  - 👎 규칙이 바뀌면(예: 한글 자모 처리, 이모지 차단) 훅 내부 한 곳만 수정하면 되지만, 그 한 곳을 반드시 훅으로 유지해야 한다 — 컴포넌트에서 직접 `setTags`를 건드리지 않도록 훅이 `tags`를 읽기 전용으로만 노출하는 것이 중요.

## Out of Scope

이번 스코프에서 **명시적으로 제외**하는 항목. 아래 항목을 이번 이터레이션에서 구현하거나 대비한 설계를 미리 넣지 않는다.

### 검색/필터

- 태그 기반 노트 검색 UI 및 API.
- 다중 태그 AND/OR 필터링.
- 태그 클릭 시 해당 태그가 달린 노트만 보여주는 뷰.
- 제목/본문/태그를 결합한 통합 검색.

### 전역 태그 관리

- 전체 태그 목록(vocabulary)을 조회/관리하는 별도 화면.
- 태그 이름 일괄 변경(rename) 및 병합(merge).
- 태그 삭제 시 모든 노트에서 동시 제거(전역 카스케이드 삭제).
- 사용 중인 태그 수 집계/통계(most used, unused 등).

### 자동완성 및 추천

- 입력 중 기존 태그 목록 기반 autocomplete drop-down.
- 본문/제목을 분석한 태그 자동 제안(AI 추천 포함).
- 최근 사용 태그 빠른 선택 칩.

### 데이터 정규화 및 마이그레이션

- 별도 `tags` 컬렉션/테이블로의 정규화.
- 태그 ID 부여 및 참조 기반 저장 구조.
- 기존 노트를 대상으로 한 태그 데이터 이관 스크립트(빈 배열 기본값 외).

### 고급 UI/UX

- 태그별 색상 지정, 아이콘, 이모지 첨부.
- 드래그 앤 드롭으로 칩 순서 변경.
- 태그 그룹/카테고리(계층 구조, 부모-자식 관계).
- 노트 목록(`NoteItem`)에서의 태그 뱃지 표시.
- 키보드로 칩 포커스 이동 및 방향키 탐색(현재 스코프는 Enter/`,`/Backspace만).

### 권한/협업/동기화

- 사용자별/팀별 태그 권한 분리.
- 실시간 협업 편집 시 태그 충돌 해결(CRDT/OT).
- 오프라인 편집 후 태그 머지 전략.

### 검증 정책 확장

- 태그 문자 집합 제한(특수문자/이모지 금지 등). 현재는 길이(15자)·개수(10개)·공백·중복만 검증한다.
- 금칙어/필터링 정책.
- 다국어 정규화(NFC/NFD), 유사어 처리.

### 성능/관측

- 태그 인덱싱, 캐싱 전략.
- 태그 변경 이력(audit log) 및 분석 이벤트 수집.

### 테스트 범위 외

- E2E 시나리오(태그 기반 검색 흐름 등)는 검색 기능 도입 시 다룬다.

## 용어 정의

| 용어                  | 정의                                                                                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **태그(Tag)**         | 노트를 분류하기 위해 부여하는 짧은 문자열. `Note.tags: string[]`에 저장된다.                                                 |
| **칩(Chip)**          | 확정된 태그 1개를 시각적으로 표현하는 pill 형태의 UI 요소. hover 시 × 버튼이 노출된다.                                       |
| **Chip Input**        | 텍스트 input과 확정된 칩 목록을 한 컨테이너에 결합한 입력 컴포넌트. Enter/`,`로 확정, Backspace로 마지막 칩 삭제를 지원한다. |
| **확정(Commit)**      | 입력 중인 텍스트를 칩으로 변환해 `tags` 배열에 추가하는 동작. 트리거는 `Enter` 또는 `,`.                                     |
| **중복**              | 대소문자를 무시한 비교(`toLowerCase()`)에서 이미 존재하는 태그. 추가 시 무시된다.                                            |
| **trim**              | 입력값 양끝의 공백 제거. trim 결과가 빈 문자열이면 확정하지 않는다.                                                          |
| **최대 길이**         | 태그 1개당 허용되는 최대 문자 수. 15자.                                                                                      |
| **최대 개수**         | 노트 1개당 허용되는 최대 태그 수. 10개.                                                                                      |
| **Placeholder**       | 태그가 0개일 때 input에 표시되는 안내 문구(`태그 입력 후 Enter`).                                                            |
| **NoteEditor**        | 노트 생성/편집 폼 컴포넌트(`src/components/NoteEditor.tsx`). 태그 UI가 배치되는 위치.                                        |
| **updateNote**        | 노트 수정 API 함수(`src/api/notes.ts`). 태그는 이 호출에 포함되어 저장된다.                                                  |
| **정규화(Normalize)** | 태그를 별도 엔티티로 분리해 ID로 참조하는 저장 구조. 이번 스코프에서는 사용하지 않는다.                                      |
