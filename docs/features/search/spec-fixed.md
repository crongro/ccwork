# Search spec-fixed

> 자체 진행 모드: /goal로 자동주행 요청을 받아 각 결정은 AI 추천안으로 채택. 근거를 함께 기록.

## 확정된 요구사항

### 기능 설명

사이드바 NoteList 상단에 검색 입력창을 배치한다.
사용자가 입력하는 키워드로 `title`과 `content`를 동시 검색하여 결과 노트만 NoteList에 표시한다.
대소문자 무시(case-insensitive), 공백 정규화(trim), 부분일치(substring). 입력은 200ms debounce.

기존 태그 필터(`selectedTag`)와 **AND 결합**한다: 태그가 선택되어 있고 검색어도 있으면 둘 다 만족하는 노트만 표시.

### 결정 사항

| 항목               | 결정                                                    | 근거(자체 채택)                                              |
| ------------------ | ------------------------------------------------------- | ------------------------------------------------------------ |
| 검색 UI 위치       | NoteList 상단 (사이드바 내부)                           | TagPanel과 같은 사이드바에 두면 필터/검색 정신 모델이 일관됨 |
| 입력 방식          | 실시간 필터 (debounce 200ms)                            | tag-filter와 동일한 즉시 반응 UX. 200ms는 키 입력 부담 완화  |
| 검색 대상 필드     | `title` + `content` (둘 다)                             | spec.md 명시                                                 |
| 매칭 방식          | case-insensitive substring (부분일치)                   | 노트 앱 표준. 정규식/형태소 분석은 과한 스코프               |
| 공백 처리          | 양끝 trim, 내부 공백은 그대로                           | 사용자가 의도치 않은 공백으로 빈 결과를 받지 않게            |
| 빈 검색어          | 검색 필터 비활성 (전체 표시)                            | 직관적                                                       |
| 태그 필터와 결합   | AND (둘 다 만족)                                        | 사용자가 좁히는 의도로 둘을 함께 쓸 것                       |
| 결과 0건 표시      | NoteList의 "노트가 없습니다" empty state 재사용         | 기존 일관성                                                  |
| 검색어 상태 위치   | `App.tsx`의 UI 상태 (selectedTag와 동일 레벨)           | CLAUDE.md 3계층 분리 원칙: UI 상태는 App                     |
| 필터 로직 위치     | `useSearchFilter` 커스텀 훅 (또는 useNoteFilter로 통합) | feedback_custom_hooks: 훅 기반 합성 선호                     |
| 하이라이트(키워드) | **이번 스코프 제외**                                    | Out of Scope 참고                                            |

### 최소 동작 시나리오

1. **제목 검색**: 검색창에 "회의" 입력 → 제목에 "회의"가 포함된 노트만 표시
2. **본문 검색**: 검색창에 "TODO" 입력 → 제목이나 본문에 "todo"/"TODO"가 포함된 노트 표시 (대소문자 무시)
3. **검색 + 태그 결합**: 태그 "work" 선택 + 검색어 "회의" → tags에 work 포함 AND (title|content에 회의 포함) 만족 노트만 표시
4. **검색어 비우기**: 검색창 비우면 (태그 필터만 적용된) 전체 노트 복원

### 경계 조건

- 빈 문자열 / 공백만 입력: 검색 필터 비활성 (전체 표시)
- 매우 긴 검색어: 길이 제한 없음. 단순 substring으로 처리
- 결과 0건: NoteList의 기존 "노트가 없습니다" 표시
- 노트 0건 상태에서 검색: 마찬가지로 "노트가 없습니다"
- title/content가 빈 문자열인 노트: 다른 필드에서 매칭되면 통과
- 한글/영문 혼합: `toLowerCase()`만으로 충분 (Locale-sensitive 비교 불필요)
- 특수문자: 이스케이프 없이 그대로 substring 비교 (정규식 아님)

### 에러 처리

검색은 클라이언트사이드 순수 함수 필터. 외부 호출 없음 → 에러 케이스 없음.
NotesContext의 loading/error는 NoteList가 이미 처리.

### 기존 UI 패턴 재사용

- NoteList의 empty/loading/error 처리 그대로
- 입력 컴포넌트는 native `<input type="search">` + 디자인 시스템 토큰
- TagPanel과 같은 사이드바 컨테이너 안에 배치

### 성능 제약

- 노트 수가 수백 건 미만이라 가정. 단순 `Array.filter` + `String.includes`로 충분
- debounce 200ms로 키 입력당 재계산 부담 완화
- 검색 인덱스, 메모이제이션, 가상 스크롤 모두 불필요

### 향후 확장 가능성

- 검색어 하이라이트: 추가 시 NoteItem prop에 `keyword?: string`을 받아 처리
- 다중 필드 토글(제목만/본문만): `searchScope: 'all' | 'title' | 'content'` 확장 여지
- 정규식/태그 검색: 검색 구문(`tag:xxx`) 파서로 확장 가능

### Out of Scope (이번 구현 제외)

- 검색어 매치 부분 **하이라이트(highlight)** 표시
- 검색 결과 정렬 옵션
- 검색 히스토리 / 최근 검색어
- 검색 범위 선택 UI (제목만 / 본문만)
- 정규식, 와일드카드, 검색 구문(`tag:`, `AND`/`OR` 연산자)
- 형태소 분석 / 유사어 검색
- 서버사이드 검색 (JSON Server `?q=` 활용 X — 클라이언트 필터 유지)
- 검색어 상태의 URL 동기화
- 다중 키워드 OR 조합

### 용어 정의 (Ubiquitous Language)

| 용어               | 정의                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| **검색어 (query)** | 사용자가 입력한 raw 문자열                                             |
| **정규화 검색어**  | trim + toLowerCase 적용된 비교용 문자열. 빈 문자열이면 필터 비활성     |
| **매칭(match)**    | 정규화 검색어가 노트의 `title` 또는 `content`(정규화)에 substring 포함 |
| **검색 필터**      | 정규화 검색어 기준으로 노트를 거르는 동작                              |
| **결합 필터**      | 태그 필터와 검색 필터를 **AND**로 함께 적용한 결과 노트 집합           |
| **빈 검색어**      | 정규화 결과가 빈 문자열인 상태. 필터 비활성으로 간주                   |
