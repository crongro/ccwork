# Search PRD

## 개요

노트의 제목과 본문을 대상으로 한 클라이언트사이드 텍스트 검색 기능을 추가한다.
사이드바 NoteList 상단의 검색 입력에 키워드를 타이핑하면 200ms debounce 후 결과 노트만 표시되며, 기존 태그 필터와 AND 결합한다.

## 사용자 스토리

- **As a** 노트 작성자, **I want** 제목/본문에 특정 키워드가 포함된 노트를 빠르게 찾고 싶다, **So that** 과거 메모를 다시 열어볼 수 있다.
- **As a** 태그로 분류해둔 사용자, **I want** 태그를 선택한 상태에서 추가로 키워드로 좁히고 싶다, **So that** 카테고리 안에서 특정 주제만 모아볼 수 있다.
- **As a** 사용자, **I want** 대소문자를 신경 쓰지 않고 검색하고 싶다, **So that** "TODO"든 "todo"든 같은 결과를 본다.
- **As a** 사용자, **I want** 검색창을 비우면 (태그 필터만 적용된) 전체 목록이 즉시 복원되길 원한다.

## 기술 결정

### ADR-1: 클라이언트사이드 substring 필터 + 커스텀 훅 합성

**Context**
검색 기능은 노트 수 수백 건 미만의 클라이언트사이드 앱에서 동작한다. 기존 태그 필터는 `useTagFilter` 훅으로 분리되어 있고, UI 상태는 `App.tsx`가 보유한다. 검색 로직을 어디에 어떻게 둘지, 그리고 태그 필터와 어떻게 결합할지가 핵심 질문이다.

**Decision**

- 검색어(`query`) 상태는 `App.tsx`에 둔다 (selectedTag와 동일 레벨).
- 클라이언트사이드에서 `Array.filter` + `String.includes`로 처리.
- 검색·태그 필터를 **하나의 커스텀 훅 `useNoteFilter(notes, { query, selectedTag })`** 로 합성한다. 기존 `useTagFilter`를 흡수하지 않고, 내부에서 `useTagFilter`를 호출해 결합하는 형태로 점진적 통합.
- 검색 입력 컴포넌트 `SearchBox`는 자체 로컬 state로 raw input을 보유하고 200ms debounce 후 `onChange(normalized)`를 호출한다. 부모는 정규화된 query만 받는다.

**Alternatives**

- **A안: useTagFilter에 query 파라미터 추가**
  - 거부 이유: 단일 책임 위반. 훅 이름과 책임이 어긋남. 결합 필터를 별도 훅으로 분리하는 편이 테스트 시그니처가 명확.
- **B안: 서버사이드 검색 (JSON Server `?q=`)**
  - 거부 이유: 비교표의 "테스트 용이성"·"기존 패턴과의 일관성" 모두 손해. NotesContext가 fetch를 한 번만 하고 메모리 캐시를 쓰는 현재 패턴과 충돌. 네트워크 라운드트립으로 debounce 비용 증가.
- **C안: NoteList 내부에서 직접 필터링**
  - 거부 이유: NoteList는 이미 props로 `notes`를 받는 표시 컴포넌트. 필터 로직을 내려놓으면 3계층 분리(컨텍스트/UI/폼)가 무너짐.

**Consequences**

- 장점: TDD 친화적 — 순수 함수성 훅이라 시나리오 작성 쉽다. 디자인 시스템 토큰만 적용하면 UI도 얇음. 기존 tag-filter 패턴과 동형.
- 단점(잃는 것):
  - 노트 수가 수천~수만 건 규모가 되면 매 키 입력마다 전체 배열 순회 → 메모이제이션/인덱스 필요. 이번 스코프에서는 감수.
  - 서버 페이지네이션을 도입할 때 검색 로직을 서버로 옮겨야 함 (재작업 비용).
  - `useNoteFilter`라는 새 추상화가 생겨, 향후 정렬·기간 필터 등을 추가할 때 이 훅이 자연스럽게 커질 위험.

### 아키텍처 3안 비교표 (자체 채택: A)

| #   | 기준             | A: 커스텀 훅 합성 (채택)      | B: 서버사이드 ?q=              | C: NoteList 내부 필터      |
| --- | ---------------- | ----------------------------- | ------------------------------ | -------------------------- |
| 1   | 데이터 구조      | 메모리의 Note[] 그대로        | JSON Server q 파라미터         | 메모리의 Note[] 그대로     |
| 2   | API 레이어 변경  | 없음                          | fetchNotes에 query arg         | 없음                       |
| 3   | 상태관리 변경    | App에 query 상태 추가         | Context에 fetch 트리거         | NoteList 내부 state        |
| 4   | 핵심 동작        | useNoteFilter 합성 훅         | debounce → refetch             | useMemo로 inline filter    |
| 5   | 컴포넌트 구조    | SearchBox + 합성 훅           | SearchBox + Context 의존       | SearchBox in NoteList      |
| 6   | 기존 패턴 일관성 | 매우 높음 (tag-filter와 동형) | 낮음 (Context fetch 모델 깨짐) | 낮음 (3계층 분리 위반)     |
| 7   | 테스트 용이성    | 매우 좋음 (훅 단위 테스트)    | 통합 테스트만 가능             | RTL로 가능하나 결합 어려움 |

## Out of Scope

- 검색어 매치 **하이라이트** 표시
- 검색 결과 정렬 옵션
- 검색 히스토리 / 최근 검색어
- 검색 범위 토글 UI (제목만 / 본문만)
- 정규식 · 와일드카드 · 검색 구문(`tag:xxx`, `AND`/`OR`)
- 형태소 분석 / 유사어
- 서버사이드 검색
- URL 쿼리 동기화
- 다중 키워드 OR 조합

## 용어 정의

| 용어               | 정의                                                                 |
| ------------------ | -------------------------------------------------------------------- |
| **검색어 (query)** | 사용자가 입력한 raw 문자열                                           |
| **정규화 검색어**  | trim + toLowerCase 적용된 비교용 문자열. 빈 문자열이면 필터 비활성   |
| **매칭(match)**    | 정규화 검색어가 노트 `title` 또는 `content`(정규화)에 substring 포함 |
| **결합 필터**      | 태그 필터와 검색 필터를 AND로 함께 적용한 결과 노트 집합             |
| **빈 검색어**      | 정규화 결과가 빈 문자열인 상태. 필터 비활성으로 간주                 |
| **debounce**       | 입력 변경 후 200ms 동안 추가 입력이 없을 때만 query 상태 갱신        |

## [GATE 2-2 / 2-4] 자체 승인

- Out of Scope 확정 (자동주행 모드로 자체 승인)
