# TDD Refactor

`tdd-green`이 모든 시나리오를 통과시킨 직후, **테스트는 SoT로 잠가두고** 구현 코드의 내부 품질만 끌어올린다. 동작은 그대로, 구조만 깔끔해진다. 매 변경마다 전체 테스트로 안전망을 확인한다.

이 스킬이 만지는 파일은 한 종류뿐이다:

- **구현 파일** — `src/` 하위 비-테스트 파일. 이슈 #N에서 변경된 파일과 그 인접 영역만.

**테스트 파일(`*.test.ts(x)`)은 절대 수정하지 않는다.** 리팩터 중 그린이 깨지면 그건 동작이 바뀐 것이고, 즉시 되돌린다. 테스트가 잘못되었다고 판단되면 `test-scenarios`로 돌아간다 — 이 스킬에서 처리하지 않는다.

## 입력

- `$ARGUMENTS` — GitHub 이슈 번호 (예: `2`)
- 슬래시 호출: `/tdd-refactor 2`
- 전제:
  - `docs/features/{feature}/issue-{N}.md`의 모든 시나리오 체크박스가 `- [x]` 상태
  - `npm test` 전체 초록
  - 변경분이 아직 커밋되지 않았거나 PR 직전 (리팩터 결과를 별도 커밋으로 분리하기 좋은 시점)

## 핵심 원칙

1. **그린은 절대선.** 매 리팩터 직후 `npm test` 전체 실행. 하나라도 빨간색이 뜨면 그 변경은 동작을 건드린 것 — 즉시 되돌리고 후보 목록에서 빼거나 방식을 바꾼다.
2. **테스트 파일 읽기 전용.** 리팩터로 인해 테스트가 깨지면 테스트를 고치고 싶은 충동이 들 수 있다. 멈춘다. 테스트 변경은 시나리오 변경이고, 그건 `test-scenarios` 스킬의 일이다.
3. **공개 동작·시그니처 보존.** 함수 이름·파라미터·반환 타입, 컴포넌트 Props, export 표면이 바뀌면 그건 리팩터가 아니라 새 기능이다. 내부 변수명·private 헬퍼·구현 분기는 자유. 의심스러우면 `issue-{N}.md`의 시그니처 섹션을 SoT로 본다.
4. **이슈 변경분 + 인접 영역만.** `git diff`로 이번 이슈가 건드린 파일을 식별하고, 그 파일과 직접 호출 관계(import)에 있는 파일만 후보로 본다. 무관한 레거시 코드를 같이 청소하지 않는다 — 그건 별도 이슈/PR.
5. **한 번에 하나.** 후보를 한 번에 모아서 제시하되, 실행은 한 항목씩 → `npm test` → 다음. 여러 개를 묶어 적용하면 그린이 깨졌을 때 어느 변경이 원인인지 분간 어렵다.
6. **임의 추상화 금지.** "나중에 재사용할 수도 있으니" 헬퍼·제네릭·HOC를 만들지 않는다. 같은 패턴이 **3회 이상 중복**될 때만 추출 후보로 본다 (Rule of Three). 이슈 변경분만으로 3회가 안 되면 추출하지 않는다.
7. **디자인 토큰 정합성 점검 (UI 한정).** UI 코드 변경분이 있으면 `docs/design-system/` 토큰을 위반한 임의 HEX/px가 섞이지 않았는지, hook 검사를 통과한 코드라도 의미적으로 토큰을 쓰지 않은 곳이 있는지 점검 후보로 올린다.
8. **승인 게이트 이중 적용.** (a) 후보 목록 제시 → 사용자 승인 → 실행 (b) 실행 중 그린이 깨지면 되돌리고 보고. 승인 없이 새 후보를 즉흥 추가하지 않는다.

## 파이프라인

```
tdd-green 산출물: 그린 그린 + issue-{N}.md (체크박스 모두 [x])
    ↓ 단계 1 — 사전 점검 (npm test 그린 확인, git diff로 변경 파일 식별)
변경 파일 목록 + 인접 호출부 매핑
    ↓ 단계 2 — 리팩터 후보 식별
중복/네이밍/구조/디자인 토큰 4축으로 스캔
    ↓ 단계 3 — 후보 제시 + [GATE] 승인
승인된 항목만 다음 단계로
    ↓ 단계 4 — 한 항목씩 적용
각 항목: 변경 → npm test → 그린 확인 → 다음
   (그린 깨지면 즉시 되돌리고 보고, 5회 한도)
    ↓ 단계 5 — 결과 요약
변경 파일·항목별 before/after·테스트 영향(없음) 보고
```

---

## 단계 1: 사전 점검

1. **이슈 파일 확인** — `docs/features/{feature}/issue-{N}.md`를 찾는다. 모든 시나리오가 `- [x]`인지 확인. `- [ ]`가 남아 있으면 멈추고 "tdd-green이 완료되지 않았습니다 (#N개 미통과)"로 보고. `tdd-green`으로 돌려보낸다.
2. **`npm test` 실행** — 전체 그린이 baseline. 하나라도 빨간색이면 멈추고 "Refactor 진입 전제 위반"으로 보고.
3. **변경 파일 식별** — `git diff --name-only $(git merge-base HEAD main)..HEAD`로 이슈 #N이 건드린 파일 목록을 뽑는다 (테스트 파일·문서 제외하고 `src/` 하위만 후보 풀로 사용). PR 베이스가 `main`이 아닌 부모 브랜치(예: `feature/tag-spec`)면 베이스를 그쪽으로 바꾼다 — 메모리의 child→parent flow 컨벤션과 일치.
4. **인접 영역 매핑** — 변경 파일이 export하는 심볼을 import하는 파일을 grep해 후보 풀에 추가. 예: `useTagInput.ts`가 변경됐다면 `useTagInput`을 import하는 `NoteEditor.tsx`도 후보 풀.
5. **간단한 보고** — "변경 파일 N개, 인접 파일 M개. 후보 스캔 진행합니다" 한 줄.

## 단계 2: 리팩터 후보 식별

다음 4축으로 후보 풀을 훑는다. 각 후보는 **(파일:라인 + 무엇을 + 왜)** 3요소로 기록한다.

### (a) 중복 제거 — Rule of Three

- 같은 표현이 **3회 이상** 반복되면 추출 후보. 2회 이하는 추출하지 않는다 (성급한 추상화).
- 예: `tags.filter(t => t !== tag)`가 한 곳에만 있으면 그대로 둔다. 세 곳에 있으면 `removeFromTags(tags, tag)` 같은 헬퍼 검토.
- 컴포넌트 단위에서는 JSX 구조 중복이 3번 이상이면 sub-component 추출 검토.

### (b) 네이밍 개선

- 모호한 이름 → 의도가 드러나는 이름으로. 예: `data` → `notes`, `handle` → `handleSave`, `flag` → `isCreating`.
- 프로젝트 컨벤션 위반: `on*`/`handle*`/`is*` prefix가 빠진 prop·핸들러·boolean.
- 줄임말·약자·임의 단축형. CLAUDE.md의 네이밍 규칙을 SoT로 본다.

### (c) 구조 개선

- **긴 함수**: 한 함수가 한 화면을 넘어가면 의미 단위로 분할 후보. 단, 추출이 가독성을 더 떨어뜨리면 그대로 둔다.
- **잘못된 위치**: 비즈니스 로직이 컴포넌트에, UI 로직이 훅에 섞여 있으면 3계층(서버/UI/폼) 규칙 위반. 옮길 후보.
- **죽은 코드**: 이번 이슈 작업 중 더 이상 호출되지 않게 된 import/변수/함수.
- **불필요한 방어 코드**: 시그니처상 도달 불가능한 null 체크/try-catch. 단, 외부 경계(API 응답·user input)는 건드리지 않는다.

### (d) 디자인 토큰 정합성 (UI 한정)

- 임의 HEX/px가 섞였는지 (`docs/design-system/01-tokens-color.md`, `03-tokens-spacing.md` 토큰과 대조).
- 같은 의미인데 다른 값을 쓴 곳 (예: chip 텍스트 색이 어떤 곳은 `#586064`, 다른 곳은 `text-slate-500`).
- `dont.md`의 금지 패턴(border, 순수 검정, rgba 그림자)이 hook을 우회해 들어왔는지.

### 후보가 없는 경우

- 정직하게 "리팩터 후보 없음"으로 보고하고 단계 5로 점프. 억지로 만들지 않는다. 작은 변경분은 처음부터 깔끔할 때가 많다.

## 단계 3: 후보 제시 + [GATE] 승인

후보 목록을 표 형식으로 제시한다:

```
| # | 파일:라인              | 분류   | 변경 내용                           | 근거                       |
|---|------------------------|--------|-------------------------------------|----------------------------|
| 1 | useTagInput.ts:23      | 네이밍 | `t` → `existing` (filter 콜백 인자) | 의도 명확화                |
| 2 | TagChipInput.tsx:24-31 | 구조   | × 버튼을 `<TagChip>` sub로 추출     | JSX 중첩 깊이 + 재사용성   |
| 3 | NoteEditor.tsx:39      | 죽은코드 | 이번 이슈로 미사용된 import 제거   | 빌드 경고                  |
```

각 항목에 `(a)` 적용 / `(s)` 스킵 / `(d)` 더 자세히 등으로 답할 수 있게 안내한다.

**[GATE]** 사용자가 적용할 항목을 명시(번호 또는 "1, 3" 식)할 때까지 단계 4로 진행하지 않는다. "다 해도 좋아" 같은 포괄 승인도 받되, 그 경우에도 한 항목씩 실행한다.

## 단계 4: 항목별 적용 루프

승인된 항목을 위에서 아래로 처리한다. 각 항목마다:

### 4-(a). 변경 적용

- 후보 표의 `변경 내용`대로만 손댄다. 인접한 다른 개선이 보여도 이번 항목 범위를 넘지 않는다 (별도 후보로 다시 올린다).
- 시그니처/공개 동작은 보존. 내부 구현만 변경.

### 4-(b). `npm test` 실행

- **그린 유지**: 다음 항목으로.
- **빨간색 발생**: 변경이 동작을 바꿨다는 신호. 즉시 되돌린다(`git checkout -- <file>` 또는 Edit으로 원복). 사용자에게 한 줄 보고:
  ```
  ⚠️ 항목 #N "<변경 내용>" — 적용 후 X개 테스트 실패. 되돌렸습니다.
  추정 원인: [동작 변경 / 시그니처 변경 / 부수효과]
  다음 액션: [방식 변경 후 재시도 / 스킵]
  ```
- **5회 시도 후에도 그린 못 만들면** 항목 자체를 포기하고 사용자에게 보고. 무한 시도 금지.

### 4-(c). 다음 항목

- 한 항목 끝내기 전에 다음 항목 코드를 미리 쓰지 않는다.

## 단계 5: 결과 요약

마지막에 한 단락 보고:

```
✅ Refactor 완료: 적용 N개 / 스킵 M개 / 실패 K개
변경 파일:
  - src/hooks/useTagInput.ts: 항목 #1 (변수명 명확화)
  - src/components/TagChipInput.tsx: 항목 #2 (TagChip sub-component 추출)
테스트 영향: 47/47 그린 유지 (회귀 없음)
다음 단계: /security-review {이슈번호} → 커밋 → PR
```

리팩터 후보가 0개였다면 그것도 명시:

```
✅ Refactor 검토 완료: 후보 없음
변경분이 작고 처음부터 깔끔합니다. 다음 단계로 진행하세요.
```

## 자주 하는 실수 (피할 것)

- **테스트가 깨졌는데 테스트를 고침**: 가장 큰 금기. 그린이 깨지면 변경을 되돌리는 게 정답이지, 테스트의 expect를 약하게 만드는 게 정답이 아니다. 시나리오 변경은 `test-scenarios` 단계로 돌아가서.
- **시그니처 변경**: "더 좋은 이름이라서" 함수명·prop명·반환 타입을 바꾸면 호출부가 깨지고 시나리오의 SoT가 틀어진다. 공개 표면은 보존, 내부만 정리.
- **무관한 파일까지 청소**: 이슈 #N 작업 중 눈에 띈 다른 파일의 코드 냄새는 별도 이슈로. 한 PR이 너무 광범위해지면 리뷰가 어렵고 회귀 영역이 커진다.
- **2회 중복으로 추출**: Rule of Three 미준수. 2회 중복은 그대로 두는 게 옳다. 헬퍼 추출은 압박이 충분히 누적된 뒤에.
- **승인 없이 즉흥 후보 추가**: 단계 4 실행 중 새로 발견한 후보를 그 자리에서 적용하지 않는다. 노트해두고 다음 사이클에서 단계 2 후보 풀에 올린다.
- **여러 항목 묶어 적용**: "비슷한 개선이라 한 번에"는 위험. 그린이 깨졌을 때 어느 변경이 원인인지 분간 안 된다.
- **그린 확인 생략**: "이건 안전한 변경이라 테스트 안 돌려도 돼"는 함정. 매번 돌린다 — 빠르고 부담 없다.
- **죽은 코드 자신만만 삭제**: "더 이상 안 쓰일 것 같아서" 삭제했더니 다른 곳에서 dynamic import로 쓰고 있었다 — grep으로 호출부 0개를 확인한 뒤에 삭제.
- **디자인 토큰 위반을 "나중에"**: hook이 통과시킨 코드라도 의미적 위반(예: 같은 의미 다른 값)은 이번에 정리. 미루면 누적된다.
- **commit 메시지 본문 누락**: 프로젝트는 commitlint가 본문 2줄 이상 요구. Refactor 단계 끝에 commit한다면 `refactor: <범위>` + 본문에 적용한 항목 수·근거를 기록.
