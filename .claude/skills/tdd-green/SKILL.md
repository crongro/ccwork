# TDD Green

`tdd-red` 스킬이 만든 **실패 테스트 + 시그니처-only stub**을 입력으로 받아, 각 테스트가 통과하는 최소한의 구현 코드를 작성한다. 한 시나리오를 빨강 → 초록으로 만들고, 회귀가 없는지 전체 테스트로 확인한 뒤, 다음 시나리오로 넘어간다.

이 스킬이 만지는 파일은 한 종류뿐이다:

- **구현 파일** — `src/` 하위 비-테스트 파일. stub의 `throw`를 진짜 동작으로 채우고, 필요한 경우 새 파일을 만든다.

**테스트 파일(`*.test.ts(x)`)은 절대 수정하지 않는다.** 테스트가 잘못되었다고 판단되면 멈추고 사용자에게 보고한다 — 시나리오 변경은 `test-scenarios`로 돌아가서 처리할 일이다.

## 입력

- `$ARGUMENTS` — GitHub 이슈 번호 (예: `1`)
- 슬래시 호출: `/tdd-green 1`
- 전제:
  - `docs/features/{feature}/issue-{N}.md`가 존재하고 시나리오 체크박스가 `- [ ]` 상태
  - `tdd-red`가 작성한 `*.test.ts(x)` 파일들이 존재
  - `npm test`가 빨간색 (모든 시나리오가 collect되고 실패 중)

## 핵심 원칙

1. **테스트가 단일 진실의 출처(SoT).** 테스트가 요구하는 동작만 구현한다. 시나리오에 없는 기능을 "있으면 좋겠다"는 이유로 추가하지 않는다 — 테스트 없는 코드는 회귀 위험만 키운다.
2. **테스트 파일은 읽기 전용.** 통과시키기 어려워서 테스트를 고치고 싶은 충동이 들면 멈춘다. 그건 시나리오의 문제이고, `test-scenarios` 단계로 돌아가야 한다. 테스트의 의도를 잘못 읽었다면 사용자에게 묻는다.
3. **한 번에 한 시나리오.** 다음 시나리오를 미리 구현해두지 않는다. 통과시킨 시나리오 1개 → 회귀 확인 → `[x]` 체크 → 다음. 동시에 여러 시나리오를 통과시키려 하면 어떤 코드가 어떤 테스트를 통과시켰는지 추적이 흐려진다.
4. **최소 구현.** stub의 `throw`를 채울 때, 시나리오를 통과시키는 가장 단순한 코드부터 쓴다. 추상화·헬퍼·범용 처리는 같은 시그니처에 대한 두 번째·세 번째 시나리오에서 자연스럽게 압박을 받을 때 도입한다 (Triangulation). 첫 시나리오부터 일반화된 코드를 쓰지 않는다.
5. **불필요한 방어 코드 금지.** 테스트가 검증하지 않는 입력 검증·null 체크·try/catch는 추가하지 않는다. 시그니처와 시나리오가 보장하는 입력 형태를 신뢰한다. 경계·예외 시나리오는 별도 `it`으로 이미 들어와 있을 것이고, 그게 빨갛게 떴을 때 그때 처리한다.
6. **디자인 문서 우선, 임의 스타일 금지.** UI 구현 시 `docs/design-system/`의 토큰·컴포넌트 스펙을 적용한다. 토큰에 없는 색상·간격·border·shadow를 즉흥적으로 만들지 않는다. 또한 시나리오·design 문서 어디에도 명시되지 않은 시각적 요소(아이콘, 애니메이션, 호버 이펙트 등)는 추가하지 않는다.
7. **회귀 확인은 매번.** 새 코드 한 줄이 다른 테스트를 깨뜨릴 수 있다. 시나리오 한 개 통과시킬 때마다 `npm test` 전체를 1회 돌린다. 빨라서 부담 없다.
8. **피드백 루프는 5회까지.** 한 시나리오를 5번 시도해도 통과 못 시키면 멈추고 보고한다. 보통 5회를 넘기는 건 (a) 테스트 의도 오해, (b) stub 시그니처와 테스트 기대 불일치, (c) 모킹 누락 — 이 셋 중 하나이고, 사용자 판단이 필요하다.

## 파이프라인

```
tdd-red 산출물: 실패 테스트 + stub + issue-{N}.md (체크박스 - [ ])
    ↓ 단계 1 — 사전 점검 (npm test 실행, collect 검증)
실패 테스트 목록 확보 + 시나리오 수와 일치 확인
    ↓ 단계 2 — 디자인 컨텍스트 로드 (UI 시나리오가 있을 때만)
docs/design-system/, issue-{N}.md "디자인 참고", CLAUDE.md
    ↓ 단계 3 — 시나리오별 Green 루프
각 시나리오: 구현 → npm test → 통과 확인(회귀 없음) → [x] 체크 → 다음
   (한 시나리오당 최대 5회 반복, 초과 시 사용자 보고 후 중단)
    ↓ 단계 4 — 커버리지 측정 (참고용, 테스트 추가 금지)
npx vitest run --coverage → 미커버 라인 보고
    ↓ 단계 5 — 결과 요약
통과 시나리오 수, 변경 파일, 미커버 부분, 다음 단계 제안
```

## 단계 1: 사전 점검

1. **이슈 파일 위치 확인** — `docs/features/{feature}/issue-{$ARGUMENTS}.md`를 찾는다. 이슈 prefix(`TAG-1` → `tag/`)로 `{feature}` 디렉터리를 식별. 모호하면 사용자에게 묻는다.
2. **시나리오 카운트 추출** — `issue-{N}.md`에서 `- [ ]` 와 `- [x]`의 총 합을 센다. 이게 _기대 시나리오 수_.
3. **`npm test` 실행** — 결과의 `Tests` 라인에서 `failed (X) | passed (Y) (X+Y)` 형태로 *실제 실행 시나리오 수*를 추출.
4. **collect 실패 감지** — _실제 실행 수_ < *기대 시나리오 수*이면 collect 단계 실패 가능성이 높다 (vitest가 import 못 하면 시나리오를 카운트조차 못 함). 다음 중 하나를 한다:
   - **import 에러가 명확한 경우**: 누락된 모듈을 식별해 `tdd-red` 컨벤션대로 시그니처-only stub을 만든다 (본문은 `throw new Error('not implemented: <name>')`). 이건 Red 단계 누락분을 메우는 것이지 Green 작업이 아니다 — stub만 채우고 비즈니스 로직은 단계 3에서 처리.
   - **원인이 불명확하거나 stub 추정이 어려운 경우**: 사용자에게 보고하고 `tdd-red` 단계로 돌아갈 것을 제안한다.
5. **실패 테스트 목록 확보** — `npm test` 출력에서 `FAIL` 표시된 테스트 파일과 `it` 이름을 모은다. `issue-{N}.md`의 시나리오 순서대로 정렬한다 (정상 → 경계 → 예외).
6. **간단한 보고** — "테스트 23개 모두 collect됨, 23개 실패. 시나리오 #1부터 시작합니다" 한 줄.

## 단계 2: 디자인 컨텍스트 로드

UI 컴포넌트(`*.tsx`) 구현 시나리오가 하나라도 있으면 **이 단계를 반드시 거친다**. 순수 함수·훅·API 시나리오만 있으면 건너뛴다.

1. **`docs/design-system/dont.md` 먼저 읽기** — 금지 패턴(border, 순수 검정, `<hr>`, rgba 그림자 등)을 머리에 넣는다. 이걸 위반하면 PostToolUse hook이 저장 시점에 차단한다.
2. **`docs/design-system/README.md` 읽기** — 토큰 파일 인덱스를 확인한다.
3. **작업 대상에 맞는 토큰만 선택적으로 Read**:
   - 색상 — `01-tokens-color.md`
   - 폰트·텍스트 — `02-tokens-typography.md`
   - 간격·레이아웃 — `03-tokens-spacing.md`
   - 카드·계층 — `04-elevation.md`
   - 컴포넌트 스펙 — `05-components/{컴포넌트명}.md`
4. **이슈 문서의 "디자인 참고" 섹션** — `issue-{N}.md`에 있으면 같이 읽는다 (없을 수도 있음).
5. **CLAUDE.md의 스타일링 컨벤션** — 컴포넌트 네이밍, props 컨벤션, named export 규칙을 다시 확인.
6. **단일 `design-system.md`가 있는 경우** — 일부 프로젝트는 분할 디렉터리 대신 단일 파일을 쓴다. `docs/design-system.md`가 있으면 그것도 함께 읽는다.

이 단계의 산출물은 머릿속의 컨텍스트뿐이다. 별도 파일을 만들지 않는다.

## 단계 3: 시나리오별 Green 루프

`issue-{N}.md`의 시나리오를 위에서 아래로 순서대로 처리한다. 각 시나리오마다:

### 3-(a). 구현

- 해당 시나리오를 통과시키는 **최소한의 코드**를 stub 파일에 작성한다 (또는 stub이 없는 경우 새 파일 생성).
- 시그니처(파라미터·반환 타입)는 그대로 유지한다. 시그니처를 바꿔야 한다면 테스트도 바뀌어야 한다는 뜻이고, 그건 이 스킬의 범위 밖이다.
- **첫 시나리오의 구현은 가능한 한 단순하게.** 예: "input.trim()을 tags에 추가" 시나리오 하나만 있으면, 그냥 `setTags([...tags, input.trim()])`을 쓰는 게 맞고 빈 입력 처리·중복 검사 같은 건 그 시나리오가 빨갛게 뜰 때 추가한다.
- **UI 구현 시**: `docs/design-system/` 토큰의 Tailwind 클래스를 그대로 쓴다. 컴포넌트 스펙이 있다면 layout·spacing·state 표현을 그대로 따른다. 토큰에 없는 값(임의 HEX, px 값)은 쓰지 않는다.
- **design 문서에 없는 시각적 요소는 추가하지 않는다.** 예: 시나리오가 "tag chip 렌더링"만 요구하고 design 문서에 호버 색이 명시되어 있지 않으면, 호버 효과를 임의로 넣지 않는다. 필요하면 사용자에게 묻는다.
- 기존 코드가 있는 경우 — `tdd-red`의 stub이 아니라 이미 동작 중인 코드 — `simplify` 스킬의 기준(작은 변경, 기존 패턴 재사용)을 적용해 최소 침습으로 수정한다.

### 3-(b). `npm test` 실행 + 회귀 확인 (피드백 루프, 최대 5회)

1. `npm test`를 실행한다 (한 파일만이 아니라 전체 — 회귀 확인 때문).
2. 결과 분석:
   - **현재 시나리오 통과 + 다른 테스트 모두 그대로**: 성공. 3-(c)로.
   - **현재 시나리오 여전히 실패**: 실패 메시지를 읽고 원인 분석:
     - assertion mismatch (`expected X to equal Y`) — 구현 동작이 시나리오와 안 맞음 → 코드 수정
     - `Cannot find module` / `is not a function` — stub 시그니처와 import가 안 맞음 → 시그니처를 `issue-{N}.md`와 대조 후 수정
     - 타입 에러 (런타임 전 collect 단계) — TS 시그니처 정합성 문제 → 시그니처 보강
   - **현재 시나리오 통과했는데 다른 테스트가 깨졌다**: 회귀. 깨진 테스트를 분석해서 원인을 찾는다 — 보통 (a) 공유 상태/모듈 캐시 오염, (b) 시그니처 변경의 부수효과. 회귀를 일으키지 않는 방향으로 다시 구현한다.
3. 1·2번을 최대 **5회까지** 반복한다.
4. 5회를 넘겨도 통과 못 시키면 **중단하고 사용자에게 보고**:
   ```
   ⚠️ 시나리오 #N "should ... when ..." — 5회 시도 후에도 실패
   마지막 에러: <에러 메시지 첫 3줄>
   추정 원인: [테스트 의도 오해 / stub 시그니처 불일치 / 모킹 누락 / 그 외]
   다음 액션 제안: [시나리오 재검토 / 시그니처 수정 / 사람이 디버깅]
   ```
   사용자 결정이 올 때까지 다음 시나리오로 넘어가지 않는다.

### 3-(c). 시나리오 체크박스 갱신

- `docs/features/{feature}/issue-{N}.md`에서 방금 통과시킨 시나리오의 `- [ ]`를 `- [x]`로 바꾼다.
- 시나리오 문장이 여러 곳에 중복되어 있으면 (Acceptance Criteria + 테스트 시나리오 섹션 등) 모두 동기화한다.
- 이 한 번의 Edit이 끝난 뒤에야 다음 시나리오로 진행한다 — 진행 상황을 파일에 즉시 반영해서 중단되어도 재개 가능하게 만든다.

### 3-(d). 다음 시나리오로

- 시나리오 순서대로 진행 (정상 → 경계 → 예외).
- 한 시나리오를 끝내기 전에 다음 시나리오의 코드를 미리 쓰지 않는다.
- 모든 `- [ ]`가 `- [x]`로 바뀌었으면 단계 4로.

## 단계 4: 커버리지 측정 (참고용)

전체 시나리오 통과 후 **한 번만** 실행한다.

1. `npx vitest run --coverage`를 실행한다 (또는 프로젝트에 `test:coverage` 스크립트가 있으면 그걸 사용).
2. 출력의 커버리지 표를 읽고, **미커버 라인이 있는 파일·함수**를 찾는다.
3. 다음 중 하나로 분류해서 사용자에게 보고:
   - **시나리오에서 빠진 케이스** — 예: 에러 분기를 시나리오가 다루지 않아서 미커버. 사용자에게 "이 분기를 다루는 시나리오를 추가할지" 묻는다 (이 스킬은 추가하지 않음 — `test-scenarios`로 돌아갈 일).
   - **방어 코드** — 시그니처상 도달 불가능한 분기. 코드를 단순화해서 분기를 없애면 커버리지가 자연스럽게 올라간다. 단, 변경은 최소 침습으로.
   - **외부 경계 (main.tsx, vite-env.d.ts 등)** — 의도적으로 coverage exclude. 무시.
4. **커버리지를 올리려고 테스트를 추가하지 않는다.** 100% 커버리지가 목표가 아니다. "테스트가 검증하는 동작"과 "실제 동작"이 일치하는 게 목표다.

## 자주 하는 실수 (피할 것)

- **테스트 파일 수정**: 통과시키기 어려워서 `expect`를 약하게 고치거나 `it.skip`을 다는 건 곧 시나리오를 거짓말로 만드는 일이다. 테스트가 잘못되었다고 판단되면 멈추고 사용자에게 보고. (이 스킬의 가장 큰 금기.)
- **테스트에 없는 기능 추가**: "이 컴포넌트엔 어차피 삭제 버튼도 필요할 텐데"라며 시나리오 없이 구현 코드를 넣지 않는다. 그건 다음 이슈의 일이고, 지금 추가하면 회귀 안전망 없이 배포된다.
- **첫 시나리오부터 범용 추상화**: 테스트가 한 케이스만 검증하는데 헬퍼 함수·제네릭 클래스로 일반화하지 않는다. 두 번째·세 번째 시나리오의 압박을 받기 전엔 단순한 코드가 옳다.
- **불필요한 방어 코드**: `if (!input) return;` 같은 가드는 시나리오가 빈 입력을 검증할 때만 추가한다. 시나리오에 없으면 없는 게 맞다.
- **디자인 토큰 무시한 임의 색**: `bg-blue-500`, `#3B82F6` 같은 즉흥 값을 쓰지 않는다. `01-tokens-color.md`에 정의된 토큰만 사용. 토큰에 없는 색이 필요하면 사용자에게 묻는다.
- **design 문서에 없는 호버/포커스/애니메이션 추가**: 명시되지 않은 시각적 표현을 임의로 넣지 않는다. 필요해 보이면 멈추고 묻는다.
- **회귀 확인 생략**: 한 시나리오 통과시키고 바로 다음으로 가지 않는다. `npm test` 전체를 매번 돌려 다른 테스트가 그대로인지 확인. 부수효과는 끝에 가서 발견하면 어떤 변경이 원인인지 추적이 어렵다.
- **체크박스 갱신 미루기**: 시나리오 통과 즉시 `[x]`로 바꾼다. "한 번에 모아서 갱신"하면 중단·재개 시 진행 상황 추적이 안 된다.
- **5회 루프 무시하고 계속 시도**: 5회를 넘겨도 통과 못 시키면 거의 항상 사람의 판단이 필요한 상황이다. 무한 시도하지 않고 멈추고 보고.
- **커버리지 100% 추구**: `--coverage` 결과의 미커버 라인을 채우려고 테스트를 추가하면 시나리오 도출 단계의 의미가 사라진다. 미커버는 보고만 하고 결정은 사용자에게 맡긴다.
- **stub 본문을 한 번에 다 채우기**: 한 모듈의 stub이 5개 메서드를 가지고 있어도 시나리오 1개에 대응하는 메서드만 먼저 구현한다. 나머지는 그 시나리오가 빨갛게 떴을 때 채운다.
- **commit 시 본문 누락**: 이 프로젝트는 commitlint가 본문 2줄 이상을 요구한다. Green 단계 끝에 commit한다면 `feat: <기능>` + 본문에 통과시킨 시나리오 수·주요 구현 결정을 기록한다.
