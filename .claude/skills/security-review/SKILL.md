# Security Review

Refactor 직후 — 모든 테스트가 초록인 상태에서 — **커밋·PR 직전 마지막 게이트**로 동작한다. 단위 테스트가 잡지 못하는 세 가지 영역을 본다:

1. **타입 안전성** (`tsc --noEmit`) — 빌드 실패를 미리 잡는다. 테스트는 모킹 때문에 타입 오류를 우회할 수 있다.
2. **의존성 취약점** (`npm audit`) — 이번 이슈의 코드가 아니라 그 코드가 깔고 앉은 `node_modules`의 위험.
3. **시크릿 노출** (`.env` ↔ `src/` 교차 grep) — `.env`의 변수가 `src/`에서 직접 참조되어 번들에 포함되거나, 키 자체가 코드에 하드코딩된 경우.

이 스킬이 만지는 파일은 매우 제한적이다:

- **타입 오류 수정**: 오류가 발생한 `src/` 비-테스트 파일 (승인된 항목만).
- **취약점 수정**: `package.json` + `package-lock.json` (승인된 안전 업그레이드만).

이 외 파일은 모두 읽기 전용이다. 특히:

- **테스트 파일(`*.test.ts(x)`)은 절대 수정하지 않는다.** 타입 오류라도 마찬가지 — 테스트가 시그니처를 강제하는 게 정상이고, 테스트를 고쳐서 통과시키는 건 안전망 훼손이다.
- **`.env*` 파일은 절대 수정하지 않는다.** 시크릿 회전·삭제는 사람의 결정이고, 이 스킬은 노출 사실만 보고한다.
- **`npm audit fix --force`는 절대 사용하지 않는다.** `--force`는 SemVer 메이저 업그레이드를 동반해 호환 깨짐을 일으킨다 — 그건 별도 의존성 업그레이드 이슈의 일이다.

## 입력

- `$ARGUMENTS` — GitHub 이슈 번호 (예: `1`)
- 슬래시 호출: `/security-review 1`
- 전제:
  - `npm test`가 전부 초록색 (Refactor가 끝난 직후라는 의미)
  - 커밋 직전 (스테이징 전 또는 후 무관, 단 이번 이슈의 코드가 워킹 트리에 반영된 상태)
  - 인터넷 접근 가능 (`npm audit`이 advisory db를 조회함)

전제가 깨져 있으면 멈추고 사용자에게 보고한다 — 빨간 테스트가 있는 상태에서는 그쪽을 먼저 해결해야 하고, 워킹 트리가 비어 있으면 점검할 변경분이 없다.

## 핵심 원칙

1. **자동 수정에 의존하지 않는다.** `tsc`·`audit`이 잡는 항목은 표면적으로 같아 보여도 컨텍스트마다 처방이 다르다. 같은 "any 사용 경고"가 한 곳에선 외부 라이브러리 한계라 의도적이고 다른 곳에선 게으름이다 — 사람이 분류 후 결정한다.
2. **3분류는 도구 출력의 단순 사본이 아니다.** `npm audit`이 "high"라고 분류해도 실제로는 dev-only 의존성이라 빌드 산출물에 영향이 없을 수 있다. 반대로 `tsc`가 "warning"이라도 시크릿이 any로 흘러가는 코드면 "즉시 수정"이다. **영향 범위(production vs dev, runtime vs build, user-facing vs internal)를 보고 다시 분류한다.**
3. **승인 없이 자동 수정 금지.** [GATE]에서 막힌다. 빌드 실패·시크릿 노출처럼 명백히 위험한 항목도 승인 후 처리. 이는 (a) 사람의 우선순위 판단을 존중하고 (b) 잘못 분류된 "즉시 수정"이 다른 회귀를 부르지 않도록 한다.
4. **테스트 파일은 읽기 전용.** 타입 오류가 테스트 파일에서 나오면 — 거의 항상 시그니처 변경이나 모킹 누락이 원인 — 멈추고 사용자에게 보고한다. 그건 `tdd-green`이나 `tdd-refactor` 단계로 돌아갈 일이지 보안 점검의 일이 아니다.
5. **`.env`의 값을 코드에 노출하는 건 거의 항상 즉시 수정.** Vite/Webpack 번들러는 `import.meta.env.X` 패턴을 빌드 시점에 치환해 클라이언트 번들에 포함시킨다. `.env`에 `VITE_` 접두 없는 시크릿이 있는데 `src/`에서 직접 참조하면, 빌드 산출물이 시크릿을 노출한다. 또한 키 자체(예: `sk-...`, `AIza...`)가 코드에 하드코딩되면 즉시 회전 권고 + 코드 제거.
6. **`--force`는 다음 이슈의 일.** `npm audit fix`는 SemVer 호환 범위 안에서만 시도하고, `--force`가 필요한 메이저 업그레이드는 별도 PR로 분리한다 — 그래야 호환 깨짐을 다른 변경과 섞지 않고 검증할 수 있다.
7. **재스캔으로 끝낸다.** 수정 후 같은 도구를 다시 돌려 0건(또는 무시 가능 항목만 남았는지) 확인. 한 번의 수정이 다른 영역을 깨뜨릴 수 있다 (타입 수정이 의존성 호출 패턴을 바꿔 새 경고를 만들거나, audit fix가 lockfile 충돌을 만들거나).
8. **이슈 컨텍스트는 분류의 가중치.** `$ARGUMENTS`로 들어온 이슈가 다루는 영역(예: 인증·결제 같은 보안 민감 영역인지, 단순 UI 변경인지)에 따라 같은 항목도 우선순위가 달라진다. 이슈 본문을 빠르게 훑어 도메인 컨텍스트를 잡아둔다.

## 파이프라인

```
tdd-refactor 산출물: 전체 테스트 Green + 워킹 트리에 변경분
    ↓ 단계 1 — 사전 점검 (전제 + 이슈 컨텍스트 로드)
npm test 초록 확인 + 이슈 본문 훑기
    ↓ 단계 2 — 3종 스캔 (병렬)
tsc --noEmit / npm audit --json / .env ↔ src/ 교차 grep
    ↓ 단계 3 — 3분류 (즉시 수정 / 권장 / 무시)
도구 출력 + 영향 범위 + 이슈 컨텍스트 가중치 → 분류
    ↓ 단계 4 — [GATE] 사용자에게 분류 보고 + 승인 대기
"즉시 수정 필요" 항목 중 적용할 것 결정
    ↓ 단계 5 — 승인 항목 처리
타입 오류 수정 / 안전한 audit fix / 시크릿 노출 제거
    ↓ 단계 6 — 재스캔
같은 3종을 다시 돌려 클린(또는 무시 가능만) 확인
    ↓ 단계 7 — 결과 요약
적용 / 미적용 / 사용자 액션 필요 항목 정리, PR 권장 메시지 제공
```

## 단계 1: 사전 점검

1. **`npm test` 한 번 더 실행** — Refactor 직후라도 워킹 트리가 추가 변경되었을 수 있다. 빨간색이면 멈추고 보고: "테스트 실패 N개. tdd-green/refactor로 돌아가 해결해주세요." 이 스킬은 테스트 실패를 직접 고치지 않는다.
2. **이슈 본문 훑기** — `docs/features/{feature}/issue-{$ARGUMENTS}.md` 또는 `gh issue view {N}`으로 이슈 도메인 파악. 인증·결제·외부 API 같은 보안 민감 영역이면 이후 분류에서 가중치 상향. 모호하면 사용자에게 묻는다.
3. **`.env` 파일 존재 확인** — 프로젝트 루트의 `.env`, `.env.local`, `.env.production` 등. 없으면 단계 2의 (c) 스캔은 "키 하드코딩"만 점검하면 된다.
4. **스캔 시작 시각 기록** — 단계 6 재스캔 결과와 비교용 (단순히 "이전 N건 → 현재 0건"이라고 보고하기 위함).

## 단계 2: 3종 스캔

세 명령은 서로 독립적이므로 **병렬 실행**한다 (한 번의 메시지에 세 Bash 호출).

### 2-(a). 타입 오류 — `npx tsc --noEmit`

```bash
npx tsc --noEmit 2>&1
```

- `--noEmit`로 컴파일 산출물은 만들지 않고 타입 검사만.
- 출력 형식: `path/file.ts(L,C): error TSxxxx: <message>`.
- 실패 코드 종류로 1차 분류:
  - `TS2304` (Cannot find name) / `TS2322` (Type not assignable) / `TS2345` (Argument not assignable) — 빌드 실패 수준 → **즉시 수정 후보**.
  - `TS6133` (declared but never read) / `TS7006` (implicit any) — 코드 품질 → **권장 수정 후보**.
  - `node_modules/...`에서 나오는 오류 — 라이브러리 타입 문제 → **무시 가능 후보** (skipLibCheck 설정 영역).
- 출력 라인 수가 1000+이면 head 100줄만 분석에 쓰고, 카테고리별 카운트만 보고한다.

### 2-(b). 의존성 취약점 — `npm audit --json`

```bash
npm audit --json 2>&1
```

- `--json`으로 파싱 가능한 형태 확보. 사람이 읽는 출력은 `npm audit` (옵션 없이).
- JSON의 `vulnerabilities` 객체에서:
  - `severity`: `critical` / `high` / `moderate` / `low` / `info`
  - `via`: 어느 의존성 경로에서 들어왔는지
  - `range`: 영향받는 버전
  - `fixAvailable`: `true` / `false` / 객체(메이저 업그레이드 필요 시)
- 1차 분류:
  - `critical` / `high` + production dep + `fixAvailable: true` (자동 호환) → **즉시 수정 후보**.
  - `moderate` + production dep — **권장 수정 후보**.
  - `low` 또는 dev-only dep (`devDependencies`만) → **무시 가능 후보** (런타임 영향 없음).
  - `fixAvailable`이 메이저 업그레이드면 → **무시 가능 후보** + "별도 의존성 업그레이드 이슈로 분리" 권고. `--force` 사용 안 함.
- production vs dev 구분은 `package.json`의 `dependencies` / `devDependencies`로 결정. 출력 JSON의 `effects`도 참조.

### 2-(c). `.env` 노출 — 교차 grep

```bash
# 1) .env 파일에서 변수명만 추출 (값은 절대 출력하지 않음)
grep -E '^[A-Z_][A-Z0-9_]*=' .env .env.local .env.production .env.development 2>/dev/null \
  | sed -E 's/=.*//' | sort -u

# 2) src/에서 시크릿 패턴 하드코딩 grep (네거티브 매치 위주)
grep -rEn "(sk-[a-zA-Z0-9]{20,}|AIza[0-9A-Za-z_-]{35}|ghp_[A-Za-z0-9]{36}|xox[baprs]-[A-Za-z0-9-]+)" src/ 2>/dev/null

# 3) 추출된 변수명을 src/에서 직접 참조하는지 (Vite는 import.meta.env.X 패턴)
# 변수명 목록을 받아 한 줄씩 grep
```

- **변수 값은 절대 출력하지 않는다.** 변수명만 다루고, 노출 위치(파일·라인)만 보고한다.
- 노출 패턴 분류:
  - **`VITE_` 접두사 없이 시크릿 같은 이름** (`*_KEY`, `*_SECRET`, `*_TOKEN`, `*_PASSWORD`)이 `.env`에 있는데 `src/`에서 `import.meta.env.X`로 참조 → Vite가 빌드 시 빈 문자열로 치환하므로 동작 안 하지만, 그 이름이 코드에 들어가 있다는 사실 자체가 **즉시 수정** (다음 PR에서 누군가 `VITE_` 접두를 붙이면 클라이언트 번들에 노출). → 변수명을 서버 측 처리(API route)로 옮기거나, 명백히 클라이언트 안전이면 `VITE_` 접두 + 동의 받음.
  - **`VITE_*_SECRET` / `VITE_*_KEY` 같은 위험한 이름** — Vite가 클라이언트 번들에 노출. → **즉시 수정** (서버로 옮김).
  - **시크릿 키 패턴이 `src/`에 하드코딩** (`sk-...`, `AIza...`, GitHub PAT 등) → **즉시 수정** + 키 회전 권고.
  - **`.env.example`에만 있는 placeholder 값** — 무시 가능.

## 단계 3: 3분류 — 도구 출력 + 영향 범위 + 컨텍스트

도구가 분류한 등급을 그대로 받지 않고 다음 가중치로 다시 분류한다.

### 가중치

| 요인                                            | 영향                                  |
| ----------------------------------------------- | ------------------------------------- |
| Production dep (런타임 번들에 포함)             | 등급 ↑                                |
| Dev-only dep (빌드 시점에만)                    | 등급 ↓                                |
| 이슈 도메인이 보안 민감 (인증·결제·외부 API)    | 모든 항목 ↑                           |
| 이번 이슈가 추가/수정한 코드의 직접 의존성      | 등급 ↑                                |
| `node_modules` 내부 (사용자 코드 아님)          | 등급 ↓                                |
| 자동 수정 가능 (`fixAvailable: true` 호환 범위) | 처리 비용 ↓ → 즉시 수정으로 묶기 쉬움 |
| 자동 수정이 메이저 업그레이드 필요              | 별도 이슈로 — 무시 가능               |

### 분류 정의

**🔴 즉시 수정 필요** — 다음 중 하나:

- `tsc`가 잡은 빌드 실패 수준 오류 (`TS2304`/`TS2322`/`TS2345` 등)
- `critical` / `high` severity + production dep + 호환 가능한 fix 존재
- 시크릿 키가 `src/` 코드에 하드코딩됨
- `VITE_*` 접두로 시크릿이 클라이언트 번들에 들어가게 되어 있음

**🟡 권장 수정** — 다음 중 하나:

- `tsc`의 코드 품질 경고 (`TS6133`/`TS7006` 등)
- `moderate` severity + production dep
- `.env` 시크릿 변수명이 `src/`에서 참조되지만 현재는 `VITE_` 미접두라 노출은 안 되는 상태 (잠재 위험)

**🟢 무시 가능** — 다음 중 하나:

- `low` / `info` severity
- dev-only dep의 취약점 (빌드 산출물 영향 없음)
- `fixAvailable`이 메이저 업그레이드 — 별도 이슈로
- `node_modules` 내부에서 발생한 타입 오류 (라이브러리 한계)
- 의도된 패턴 (예: `tsconfig.json`에서 명시적으로 무시하기로 한 영역)

### 보고 형식

```
🔴 즉시 수정 필요 (N건)
  [ID] 종류:위치 — 한 줄 묘사
    영향: <production/dev, runtime/build, user-facing/internal>
    제안: <구체적 수정 방향>
    위험도: <빌드 실패 / 시크릿 노출 / RCE / DoS / ...>

🟡 권장 수정 (M건)
  ...

🟢 무시 가능 (L건)
  ...
```

각 ID는 단계 5에서 처리 단위로 사용한다. 동일 원인의 여러 출력은 한 ID로 묶는다 (예: 같은 라이브러리에서 나온 5개 audit 항목 = 1 ID).

## 단계 4: [GATE] 분류 보고 + 사용자 승인

3분류 보고를 사용자에게 보여주고 **"즉시 수정 필요"** 중 처리할 항목을 묻는다.

```
⚠️ 다음 단계: "즉시 수정 필요" N건 중 처리할 항목을 알려주세요.
   - "전체" / "다 해줘" → 전체 진행
   - "1, 3" → 해당 ID만
   - "1번 빼고" → 그 항목 제외
   - "권장 수정도 같이" → 🟡까지 포함
   - "재분류 필요" → 단계 3으로 돌아가 가중치 재검토

승인 전에는 코드를 수정하지 않습니다.
```

응답 패턴은 `tdd-refactor`의 GATE와 동일하게 처리한다.

**🔴 항목이 0건**이면 단계 5는 건너뛰고 단계 6 재스캔도 생략, 단계 7 요약으로 직행. "이미 클린, 커밋해도 안전" 한 줄 보고.

승인이 명확하지 않으면 한 번 더 묻는다. **승인 없이 단계 5로 넘어가지 않는다.**

## 단계 5: 승인 항목 처리

승인된 ID를 순서대로 처리한다. 각 ID의 종류에 따라 처방이 다르다.

### 5-(a). 타입 오류 처리

- 오류 라인을 Read해 컨텍스트 확인.
- 처방:
  - `Cannot find name X` — 누락된 import 추가 (해당 모듈을 찾아서).
  - `Type X is not assignable to type Y` — 시그니처를 사용처와 일치시키거나, 호출처에서 타입을 좁힌다 (assertion보다 type guard 우선).
  - `implicit any` — 명시적 타입 부여. 타입을 정말 모르겠으면 `unknown`으로 두고 사용 시점에 narrow.
- **테스트 파일에서 발생한 오류는 절대 만지지 않는다.** 멈추고 사용자에게 보고: "테스트 파일 X에서 타입 오류 — `tdd-green`/`tdd-refactor`로 돌아가야 합니다."
- 한 항목 수정 후 즉시 `npx tsc --noEmit`을 다시 돌려 그 오류가 사라졌는지 + 새 오류가 안 생겼는지 확인. 새 오류가 생기면 롤백 후 다른 접근.

### 5-(b). 의존성 취약점 처리

- **첫 번째 시도**: `npm audit fix` (옵션 없음). SemVer 호환 범위 안에서만 업그레이드.
- 완료 후 `git diff package-lock.json package.json`으로 변경 범위 확인. 호환 깨짐 가능성이 있으면 사용자에게 보고하고 멈춘다.
- **`npm audit fix --force`는 절대 사용하지 않는다.** `fixAvailable`이 메이저 업그레이드를 요구하면 그 항목은 단계 4에서 이미 "무시 가능 + 별도 이슈"로 빠져 있어야 한다. 만약 빠지지 않고 들어왔다면 다시 사용자에게 묻는다.
- audit fix 후 `npm test` 한 번 더 돌려 의존성 변경이 동작에 영향을 주지 않았는지 확인. 깨지면 lockfile 롤백 (`git checkout -- package-lock.json package.json`).

### 5-(c). 시크릿 노출 처리

- **시크릿 키가 코드에 하드코딩**된 경우:
  1. 그 키를 코드에서 제거 (변수로 빼고 `.env`로 옮기거나 서버 측으로 이동).
  2. 사용자에게 **즉시 키 회전** 권고: "이 키가 git history에 남았을 가능성이 높습니다. 로테이션 대상입니다. 이 스킬은 history는 만지지 않습니다." `git filter-repo` 같은 history 재작성은 별도 작업.
- **`VITE_*` 접두 시크릿** — `.env`에서 그 변수의 `VITE_` 접두를 제거하고, `src/`에서 참조처를 서버 측 호출로 바꾼다. 이건 아키텍처 변경 수준이라 보통 단계 4에서 사용자가 명확히 승인한 경우에만 진행. 모호하면 보고 후 사용자 결정.
- **`.env` 파일 자체는 만지지 않는다.** 변경이 필요하면 보고만 하고 사용자가 직접 수정.

### 5-(d). 항목 단위 점검

각 ID 처리 후:

- ✓ 그 도구의 해당 항목이 사라졌는지 재확인 (전체 재스캔은 단계 6에서, 여기선 빠른 spot check).
- ✓ `npm test` 초록 유지.
- ✗ 다른 항목이 새로 생겼으면 롤백 후 사용자 보고.

## 단계 6: 재스캔

승인 항목을 모두 처리한 뒤, 단계 2와 동일하게 3종을 **병렬** 재실행해 결과 비교.

```
재스캔 결과:
  tsc:        시작 N건 → 종료 0건 ✓
  npm audit:  시작 critical 2 / high 5 → 종료 critical 0 / high 1 (메이저 업그레이드 필요 — 별도 이슈)
  env 노출:   시작 1건 → 종료 0건 ✓
```

- 즉시 수정 필요 항목이 0건으로 떨어졌으면 클린.
- 잔여 항목이 있다면 (예: 메이저 업그레이드 필요한 high) **별도 이슈로 분리 권고**를 단계 7에 적는다.
- 재스캔이 새 항목을 발견하면 (드물지만 있음) — 다시 단계 3 분류부터.

## 단계 7: 결과 요약

```
✅ Security Review 완료

스캔 결과 (시작 → 종료):
  tsc:        12건 → 0건
  npm audit:  critical 2 / high 5 / moderate 3 → 0 / 1 / 3
  env 노출:   1건 (시크릿 하드코딩) → 0건

처리:
  [1] tsc TS2322 — src/api/notes.ts:32 응답 타입 narrow
  [2] tsc TS6133 — src/hooks/useTagInput.ts:1 미사용 import 제거 (권장이었으나 같이 처리)
  [3] npm audit — semver 호환 범위 내 자동 업그레이드 (5건 해소)
  [4] env — src/api/keys.ts에 하드코딩된 OPENAI_API_KEY를 .env로 분리

미처리 (사용자 액션 필요):
  - npm audit high 1건: vite 메이저 업그레이드 필요 → 별도 이슈 권장
  - 시크릿 회전: OPENAI_API_KEY는 git history에 남아 있을 가능성 — 즉시 로테이션 권고

테스트: 시작 N개 통과 → 종료 N개 통과 (회귀 0)
변경 파일: src/api/notes.ts, src/hooks/useTagInput.ts, src/api/keys.ts, package.json, package-lock.json
다음 단계: PR 생성 (커밋 본문에 위 변경 요약 + 별도 이슈 권고 포함)
```

## 자주 하는 실수 (피할 것)

- **`npm audit fix --force` 사용**: 메이저 업그레이드를 동반해 호환 깨짐을 만든다. 다른 변경과 섞여 회귀 추적이 어려워진다. 별도 PR로 분리하라고 사용자에게 권고. (이 스킬의 가장 큰 금기.)
- **테스트 파일의 타입 오류를 직접 수정**: 테스트 파일에서 타입 오류가 나오면 거의 항상 시그니처 변경의 결과다 — 그건 `tdd-green`/`tdd-refactor`로 돌아갈 일. 테스트를 고쳐서 통과시키면 안전망이 사라진다.
- **`.env` 파일을 직접 수정**: 시크릿 회전·삭제는 사람의 결정이고 운영 시스템과 맞물려 있다. 노출 사실만 보고.
- **시크릿 값을 출력에 포함**: 변수명·파일·라인까지만. `.env`의 실제 값을 grep 결과로 흘리지 않는다 — 로그·전사·세션 기록에 영구 남는다.
- **dev-only 취약점을 즉시 수정으로 분류**: `devDependencies`만의 취약점은 빌드 산출물에 영향이 없다 (eslint, vitest, husky 등). 시간 낭비 + 잠재 호환 문제만 부른다.
- **`tsc` warning을 모두 즉시 수정으로 묶기**: 코드 품질 경고는 권장 수정. 즉시 수정에 섞으면 PR 단위가 부풀고 리뷰가 어려워진다.
- **`node_modules` 내부 타입 오류 수정 시도**: 라이브러리 자체 문제는 사용자가 못 고친다. `skipLibCheck` 설정 또는 라이브러리 이슈 트래커가 답이다.
- **단계 4 [GATE] 건너뛰기**: 명백히 위험한 항목도 승인 후 처리. 자동 수정의 부작용을 사람이 결정 흐름에 넣어야 한다.
- **재스캔 생략**: 한 번의 수정이 다른 영역을 깨뜨릴 수 있다. 재스캔은 비용이 거의 없는 안전망이고, "처리했다"가 "해결됐다"와 같은지 확인하는 유일한 수단이다.
- **시크릿 history 잔존을 코드 제거로 끝낸 줄 안다**: 한 번 git에 push된 시크릿은 history에 영구 남는다. 코드에서 지웠더라도 키는 이미 노출된 것 — 즉시 로테이션 권고를 단계 7 요약에 포함한다. (`git filter-repo` 같은 history 재작성은 이 스킬의 범위 밖이다.)
- **commit 시 본문 누락**: 이 프로젝트는 commitlint가 본문 2줄 이상을 요구한다. Security review 결과로 커밋한다면 `fix: <영역>` 또는 `chore: security review` + 본문에 단계 7 요약(처리 N건 / 미처리 / 회귀 0)을 기록한다.
